# Focused high P-code data-flow metadata

`tools/ghidra/ExportFunctionPcodeFlow.java` is the next clean-room evidence tool after the broad program index and the numeric operand exporter. It is intended for cases where call/address proximity is known but a reconstructed field or runtime action must not be implemented until the value flow is proven.

The exporter processes exactly one analyzed function through Ghidra's decompiler and writes **metadata only**. It does not write instruction bytes, assembly/disassembly text, decompiled C text, string contents or source assets.

Each TSV row records:

- function entry;
- P-code operation address and sequence time;
- P-code opcode;
- one stable dependency token for the operation output;
- dependency tokens for data inputs;
- resolved direct-call entry/name when available.

For `CALL`/`CALLIND`, the call target is kept separate from the data-input list. This lets downstream tooling trace values through `COPY`, casts, `MULTIEQUAL`, floating-point operations and other recovered SSA operations without accidentally treating the callee address as input data.

## Export

Run inside the user's analyzed Ghidra project:

```text
ExportFunctionPcodeFlow.java <function-address-or-name> <output.tsv>
```

The project-neutral implementation and TSV row schema now live in the sibling
`revenginstr` repository as `REVENGINSTR.GhidraFunctionPcodeFlow/1`. The runners
for this exporter prefer that shared script when it is available and retain
this local copy as fallback. Both implementations keep the legacy header and
are checked for byte-for-byte parity on the same analyzed project. Current
source hashes are recorded in [source audit](../evidence/ghidra-exporter-source-parity-audit.md),
and bounded forward/reverse output parity is recorded in
[same-program parity evidence](../evidence/ghidra-export-parity.md).

For the current player-start boundary:

```text
ExportFunctionPcodeFlow.java GameScene::loadGameSceneList /tmp/loadGameSceneList-pcode.tsv
```

The output columns are:

```text
function_entry  op_address  op_time  opcode  output  inputs  callee_entry  callee_name
```

Varnode tokens are intentionally structural rather than decompiler variable names. A defined value uses the defining P-code sequence (`def:<address>:<time>:<size>`); constants and unresolved inputs use explicit storage/constant tokens. This avoids treating autogenerated decompiler variable names as evidence.

## Trace

`tools/ghidra/trace_pcode_flow.py` performs a bounded backward dependency walk from data inputs of a sink call to outputs of matching source calls.

For the two scene-list values already proven to be read through `CCString::floatValue`:

```bash
python tools/ghidra/trace_pcode_flow.py \
  /tmp/loadGameSceneList-pcode.tsv \
  --source 'CCString::floatValue' \
  --sink 'CCPoint::CCPoint'
```

A second query can test the assignment boundary:

```bash
python tools/ghidra/trace_pcode_flow.py \
  /tmp/loadGameSceneList-pcode.tsv \
  --source 'CCString::floatValue' \
  --sink 'CCPoint::operator='
```

The tracer reports only paths supported by dependency tokens. It does not infer a path because calls are adjacent. Depth and result counts are bounded (`--max-depth`, `--max-paths`) and cycles are rejected.

## Evidence interpretation

A recovered path from both `floatValue` calls into the `CCPoint` constructor would support the narrow claim that the two parsed scene-list scalars construct that point. It would still **not** by itself prove that the point is applied to the player node; that requires tracing the point onward to a player-placement consumer or recovering the semantics of `GameScene::adjustPlayerPos(int)`.

Conversely, `no data-flow path found` means only that the current analyzed/decompiled function did not expose such a path to this bounded metadata walk. Unresolved indirect calls, incomplete analysis or a value retained through memory may require a more targeted probe. Absence must not be turned into guessed runtime behavior.
